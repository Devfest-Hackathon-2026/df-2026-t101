# ADR-0010：手は3Dメッシュで表し、握りはその手の面から作る（メッシュ復元を複数フレームで合成し、1円玉で実寸にする）

> **2026-11-10 の注意**：本文は決めたときの記録です。今の動きは、下の「2026-11-10 追記」と [docs/README.md の「11/10 時点の現状」](../README.md#1110-時点の現状先に読む) を見てください。

> **このドキュメントで決めたこと**
> 1. 手は、送ったフレーム（最大8枚）ごとにSAM 3D Bodyで手のメッシュを復元し、姿勢と形のパラメータを1つにまとめ、1円玉で測った指の長さに合わせて実寸（mm）にした**3Dメッシュ**で表す。角度・指の太さ・握りを置く場所も、このメッシュから出す。
> 2. 道具の形は、手のメッシュの符号付き距離場から作る。2026-11-07 更新：形を「握り」からこぶしにかぶせるカバーに変えた（[ADR-0011](0011-dorsal-cover.md)）ので、握りからくり抜くのではなく、手の面から距離 c〜c＋t の層を殻にする（c＝すき間 `HAND_CLEARANCE_MM`、t＝カバーの厚み）。距離場とマーチングキューブで閉じたSTLにし、OpenSCADは `import()` してスリット・空気穴・レールを足す。カプセルは、切る位置を決める目安にだけ使う。
> 3. 手のメッシュは採寸の一部として保存する（持ち主とOTだけが読める）。動画とフレームは、今までどおり保存しない。同意の画面に「手の形の3Dデータを保存する」ことを足す。メッシュ復元に失敗したら、今までどおりMediaPipeの値では代わりにしない。

## 背景

- 最初の構想は「手の3Dモデルを作り、そこから手に合う形を逆算する」こと。プロトタイプ（proto ブランチ）では、指をカプセル（両端が丸い円柱）で近似した。カプセルは関節の位置と太さの目安だけで、手のひらのふくらみ、指の断面の形、指どうしの段差は表さない
- プロトタイプで、SAM 3D Body は角度だけでなく、手の表面の3Dメッシュ（頂点と三角形）も出すことが分かった（[measurement.md §11](../measurement.md#11-手のメッシュ復元)）。すでに全員から同意を得てフレームを送っているので、メッシュを使っても、送るものは増えない
- 2026-11-07、チームで「手を3Dにする方法」を比べ、メッシュ復元の合成を選んだ（下の表）

## 比べた案

| 案 | 中身 | 良い点 | 困る点 | 判断 |
|---|---|---|---|---|
| A カプセル（ADR-0008） | 関節の位置と太さの目安から、指をカプセルで組み立てる | 軽い。式が単純で検査しやすい | 手の表面の形は使わない。指の太さは仮の比（関節の間隔×0.9など） | 置き換える（位置決めと検査の目安にだけ残す） |
| **B メッシュ復元の合成** | フレームごとにSAM 3D Bodyで手のメッシュを出し、姿勢と形を1つにまとめ、1円玉で実寸にする | 今の撮影の流れのまま使える。手のひらと指の表面の形が入る。手の形の型（MHR）に沿うので、穴や欠けのない閉じた面になる | 手の形の型に寄るので、むくみや変形の細部は正確には出ない。大きさは1円玉で合わせる必要がある | **採用** |
| C 表面の直接の再構成 | 動画からフォトグラメトリや3D Gaussian Splattingで、手の表面そのものを作る | 変形も含めて表面がそのまま出る | 手を10秒以上完全に止める必要がある。重く、失敗しやすい。11/10までに仕上がらないおそれが大きい | 使わない |
| D 合成＋輪郭での補正 | Bのあと、各フレームの手の輪郭に合うよう、形を補正する | Bより正確 | 作る量が増える | 拡張機能（11/9 21:00までに入らなければ見送る） |

## 中身

### 1. 合成（`hand-mesh` が行う）

| 段階 | 方法 | 理由 |
|---|---|---|
| フレームごと | 手のデコーダで、MHRの手の姿勢と形のパラメータ、関節の3D位置、メッシュの頂点を出す。左手は画像を左右反転して右手として推定し、最後に鏡像に戻す（手のデコーダは右手だけのため） | プロトタイプと同じ |
| 1つにまとめる | 有効なフレームの、手の姿勢のパラメータ（関節ごとの回転）と形のパラメータの**中央値**を取り、MHRのモデルで1つのメッシュを作り直す。中央値から大きく外れたフレーム（関節の角度の差が中央値から30度超）は外して取り直す | 1枚だけ外れたフレームに引っぱられないため。頂点の平均ではなくパラメータでまとめるのは、向きの違うフレームの頂点はそのままでは重ならないため |
| 手の部分を切り出す | MHRの体全体のメッシュから、右手の関節に主に結び付いた頂点（スキニングの重みで判定）と、それを結ぶ三角形だけを残す。手首の切り口は平らな面でふさぎ、閉じた面にする | 握りの計算には、閉じた面（内と外が決まる）が要る |
| 返すもの | 手の座標系（[measurement.md §8.1](../measurement.md#81-手の座標系)）に置いた、**大きさを合わせる前**のメッシュ（頂点・三角形）、関節の位置、関節の角度とばらつき、署名付きの結果トークン | 大きさ（1円玉）はブラウザ側の値なので、生成APIで合わせる |

**11/7のスパイクで確かめたこと**（手元の RTX 4070 Ti SUPER。SAM 3D Body の `facebook/sam-3d-body-vith`）

| 項目 | 結果 |
|---|---|
| 手のデコーダの出力 | 形 `shape`（45個）、体の比率 `scale`（28個）、両手の姿勢 `hand`（54個×2）、体全体のメッシュ（頂点18,439・三角形36,874）、キーポイント70点（右手は21〜41、手首は41）。形・比率・姿勢が別々に出るので、パラメータで合成できる |
| 合成 | 有効なフレームの `shape`・`scale`・`hand` の中央値を、手のヘッドの `mhr_forward` に渡す（体の向き・体の姿勢・表情は0）。手首を基準にした決まった向きの手ができる（0.014秒） |
| 手の部分の切り出し | 「一番近いキーポイントが右手の頂点」では体まで入った（体のキーポイントがまばらなため）。**手首の面（手首→中指の付け根の向きを法線とし、手首から5mm指側）で切り、手首から手の長さ×1.4以内**にすると、手だけが残る（頂点約2,300・三角形約4,500）。切り口は1つの輪になり、重心への扇形でふさぐと閉じた面になる |
| 時間 | 読み込み48秒（起動時に1回）。1フレームの推論は初回約1秒、以降約0.2秒 |
| くり抜き | 距離場とマーチングキューブで、すき間0.5mmの立体を作り、OpenSCAD（Manifold）で引けた。格子0.5mm・約140万点で約12秒、OpenSCADは0.2秒。注意：①くり抜く立体の面は外向きにそろえる（裏返しだと、引いたつもりが足される）②手は計算の箱からはみ出すので、内外は手全体のボクセルで決める。ただし表面から2mm以内は、一番近い面の法線で決める（ボクセルだけでは面が階段になる）③距離は、表面の近くでは一番近い面の平面までの距離を使い、距離場を少しぼかす（点の拾い方のばらつきでざらつくため） |
| 残り | MHRの手は粗い（約2,300頂点）ので、くり抜いた面に角が見える。ループ細分割で1段細かくする。握りの軸の位置は、カプセルのすき間の計算（§3の1）で決める |

### 2. 実寸にする（生成APIが行う）

> 2026-11-10 追記：下の式（指の12区間）は最初の案。実装は手の甲の4区間の比の中央値×`length_factor`（上の「状態」と [measurement.md §8.2](../measurement.md#82-メッシュの合成と実寸化)）。`MESH_SCALE_INCONSISTENT` は、手の甲の4つの比の四分位範囲が中央値の10%を超えるか、指の12区間の比の中央値が4区間からの倍率と15%以上違うときに出す

```
k_f,s = （1円玉で測った区間の長さ） ÷ （メッシュの関節どうしの長さ）   … 人差し指〜小指の3区間ずつ、12個
k = median(k_f,s)          … 全体の倍率。メッシュの頂点に掛ける
```

- 12個の比の四分位範囲が中央値の10%を超えたら `MESH_SCALE_INCONSISTENT` を記録し、OT画面で目立たせる（指ごとの長さの比が、手の形の型と本人とで違う）
- 指ごとに倍率を変える方法は、指の付け根でメッシュが裂けるので、MVPではしない

### 3. 握りを作る（生成APIとOpenSCAD）

> 2026-11-07 更新：この節は「握り」を作る前提で書いた。形はこぶしにかぶせるカバーに変わった（[ADR-0011](0011-dorsal-cover.md)）。距離場・マーチングキューブ・面の向き・内外の決め方（下の手順2と、スパイクの注意①〜③）はカバーの殻にもそのまま使う。握りの軸（手順1）と、握り本体から引く手順（手順3・4）は使わない。殻の作り方は [generation-pipeline.md](../generation-pipeline.md) と [parts-library.md](../parts-library.md) を正とする。

1. **握りの軸**：メッシュの関節と、メッシュから測った指の太さでカプセルを組み立て、今までどおり人差し指と小指のすき間の円の中心を結ぶ（[measurement.md §8.3・§8.4](../measurement.md#83-カバーの目印手の座標系の上)）
2. **くり抜く立体**：手のメッシュの符号付き距離 `sdf(p)`（手の中が負）を、握りの外接箱（＋10mm）の中だけ、0.5mmの格子で計算し、`sdf(p) < HAND_CLEARANCE_MM` の領域の境界をマーチングキューブで面にする。これを握りの座標系に直し、閉じたSTL（`cavity.stl`）として書く
3. **OpenSCAD**：`difference() { grip_body(); import("cavity.stl"); }`。くり抜きの角は、オフセットの分だけ自然に丸くなる
4. **検査**：描いたあとのメッシュで、穴（柄を通す穴）まわりの残りの壁の厚さ（`MIN_WALL_AROUND_BORE_MM` 以上）と、張り出し（R6）を、実際の形で確かめる。カプセルの式（`MAX_CARVE_RATIO`）は、Geminiに渡す目安と、描く前のふるい分けにだけ使う

- オフセットの量 `HAND_CLEARANCE_MM` は、プロトタイプの `CAPSULE_CLEARANCE_MM` と同じ役割（採寸のずれを吸収する）。既定0.5mm（仮）としたが、カバー方式（ADR-0011）では、フェルトの厚みを含めて既定1.5mm（仮）に変えた。11/9の朝の `clearance_test` で決める
- 握りの太さ（`press_depth_mm`）は、今までどおり、すき間の円より太くする量。太くした分だけ手のメッシュが握りに食い込み、くぼみになる

### 4. 保存と見せ方

| 項目 | 決めたこと |
|---|---|
| 保存 | 実寸にした手のメッシュ（手の座標系、mm）を、ケースの採寸の版ごとに Cloud Storage へ保存する（`cases/{caseId}/hand/{measurementVersion}.glb`）。読めるのは持ち主と、担当のOTだけ |
| 見せ方 | S5（採寸の確認）で、手のメッシュを3Dで見せる（すき間の円と握りの軸を重ねる）。S7（プレビュー）と確認用画像では、握りに手のメッシュを半透明で重ねる |
| 同意 | 撮影の前の同意の画面に「手の形の3Dデータ（写真ではありません）を、作った形を確かめるために保存します。ケースを消すと消えます」を足し、同意の文の版を上げる |

## 引き受けること

| 危険 | 対策 |
|---|---|
| 曲がったまま固まった指では、メッシュ復元が手の形の型に寄り、角度や太さを小さく見積もるおそれ（学習データの分布の外） | MediaPipeの角度を比較用に並べ、差が15度を超える関節は目立たせる（ADR-0008と同じ）。S5で本人と家族が3Dの手を見て「ずれている」を選べる |
| むくみ・変形の細部は出ない | すき間（当時は0.5mm。カバー方式では1.5mm（仮））で吸収する。OTの確認を必ず通す。11/9の試し刷りで、握ったときの当たりを確かめる |
| 倍率が1つなので、指ごとの長さの比が型と違うと、一部の指が長すぎ・短すぎになる | `MESH_SCALE_INCONSISTENT` で知らせる。指ごとの倍率は拡張機能 |
| 生成APIの処理が増える（距離場とマーチングキューブ） | 計算を握りの外接箱の中だけ、0.5mmの格子に限る（約200×120×120点）。時間は11/8に測る（要確認） |
| 手の形の3Dデータを保存することへの不安 | 写真ではないこと、何のために保存するか、消し方を同意の画面に書く |
