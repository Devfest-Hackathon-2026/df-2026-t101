# ADR-0008：手はカプセルのモデルで表し、握りからくり抜く。角度はメッシュ復元で出す（全員、同意を得て送る）

> **このドキュメントで決めたこと**
> 1. 手は、指の区間をカプセル（両端が丸い円柱）で表したモデルにする。長さ・角度・太さから組み立て、握り本体からくり抜いて（`difference()`）、くぼみを指に沿わせる。
> 2. 角度は、手のメッシュ復元（SAM 3D Body）で出す。全員、撮影の前に同意を得たうえで、手を切り抜いたフレームを最大8枚、GPUのサービスに送る（同意しないと採寸に進めない）。保存はせず、返すのは角度だけ。
> 3. メッシュ復元が失敗しても、MediaPipeの角度で自動的に代わりにすることはしない（2026-11-07、チームの決定）。再試行して待ち、それでもだめなら、そのケースを止めてやり直してもらう。MediaPipeの角度は、OT画面に比較用として出すだけにする。

- 状態：採用（2026-11-07、チームの決定で、全員の映像を送る方針と、MediaPipeで代わりにしない方針に変えた）。2026-11-07：決めたこと1（カプセルでくり抜く）は [ADR-0010](0010-hand-mesh-fusion.md) で置き換え。2・3は引き続き有効

## 背景

- 最初の構想は「MediaPipeと手の表皮に点を置いて3Dモデルを作り、そこから手に合う形を逆算する」こと。これを、関節の点と指の太さから表皮を近似する形で実現したい
- MediaPipeは関節の中心しか返さない。worldLandmarksは平均的な手の大きさからの推定値で、個人の寸法には使えない
- 最初の方針は「手の写真はサーバーに送らない」だった。メッシュ復元は数億パラメータのモデルで、ブラウザでは動かないため、使うには映像を送る必要がある

## 比べた案（手のモデル）

| 案 | 良い点 | 困る点 |
|---|---|---|
| カプセルのモデル | 軽い。関節の位置が取れれば、曲がった指でもそのまま形になる。太さは本人の値。OpenSCADでそのままくり抜ける | 表皮の細かい形は再現しない |
| 手のメッシュ復元 | 1フレームから3Dの姿勢が出る | 大きさ（mm）は決まらない。長さは平均的な手に寄る。GPUが要る。変形の強い手では角度がずれるおそれ |

→ 形はカプセルで作り、角度だけをメッシュ復元で補う。値ごとの担当は次のとおり。

| 値 | 出し方 |
|---|---|
| 指の区間の長さ（mm） | 動画と1円玉（上位20%のフレームの中央値） |
| 関節の曲がり角・指の向き | メッシュ復元（送ったフレームの中央値）。MediaPipe（方法A・B）の値は、比較用としてOT画面に出すだけ |
| 指の太さ（mm） | 隣り合う関節の間隔（MVP）。輪郭から測る方法は拡張 |

## メッシュ復元モデルの選定（2026-11-07時点で、公式のリポジトリとライセンスを確認）

| 候補 | ライセンス | MANO | 手の精度（FreiHAND、PA-MPJPE） | 判断 |
|---|---|---|---|---|
| **SAM 3D Body**（Meta、2025-11公開） | コードと重みはSAM License。商用を禁じる条項は見当たらない。配布するときはライセンス文を添え、発表物には利用を明記する。重みはHugging Faceで利用を申請する（承認制） | 使わない（手の形はMHR。Apache-2.0） | 5.5（論文の表。手専用のモデルを上回らないと、論文自身が書いている） | **採用**。賞金付きのハッカソンやピッチと矛盾しにくい。チームに使い慣れた人がいる |
| HaMeR | コードはMIT。重みのライセンス表記は未確認 | 必要。MANOは非商用の研究・教育・芸術だけに限られ、個人単位の許諾で、共有・再配布は禁止 | 6.0 | 使わない。使うなら、先にMANOの窓口（ps-license@tue.mpg.de）に、賞金付きの学生ハッカソンで使えるかを問い合わせる |
| WiLoR | CC BY-NC-ND 4.0（非営利、改変物の共有禁止）。依存するUltralyticsはAGPL-3.0 | 必要 | 5.5 | 使わない（縛りが一番多い） |

共通の注意：3つとも、拘縮や変形のある手での評価はない。HaMeRとWiLoRは「極端な指の姿勢で失敗する」と公式に書いている。曲がったまま固まった指は学習データの分布から外れるので、角度を小さく見積もったり、平均的な形に寄せたりするおそれがある。そのため、MediaPipeの角度（方法A・B）も同時に出し、差が大きい関節はOT画面で目立たせる。

## 映像を送るときの決まり

| 項目 | 決めたこと | 理由 |
|---|---|---|
| 同意 | 動画を撮る前に、1画面で「何を・どこへ・何のために送り、どう扱うか」を示し、「同意して進む」「やめる」を選んでもらう。同意しないと採寸に進めない。同意した日時と文の版を、生成APIがケースに記録する（`POST /consent` → `mesh_consent_at`）。`hand-mesh` は推論の前に、生成APIは採寸の保存のときに、この記録を確かめる。`hand-mesh` の結果には署名付きのトークンを付け、生成APIが確かめる（メッシュ復元を通らない角度を受け付けないため） | 手の映像は、病気や障害が分かる情報になりうる（個人情報保護法の要配慮個人情報に当たるかは要確認）。送ることを必須にする以上、何を送るかをはっきり示して同意を得る |
| 送るもの | MediaPipeで見つけた手の範囲を、少し広げて切り抜いたフレームを、向きの違うものから最大8枚。長い辺512pxのJPEGにする。1円玉や背景は入れない | 必要な最小限にする |
| 送り先 | ブラウザから、GPUのサービス（`hand-mesh`）へ直接送る。生成APIは経由しない | 生成APIが映像を一度も受け取らない作りを保つ |
| 扱い | メモリの中だけで処理し、ディスク・Storage・ログに残さない。返すのは角度（度）だけ | — |
| 場所 | Cloud Run GPUはシンガポール（asia-southeast1）。国外で処理されることを同意の画面に書く | 東京ではGPUが使えないため（[ADR-0009](0009-gpu-placement.md)） |
| 失敗したとき | 起動中（503）や時間切れは、自動で最大3回やり直す（合わせて最大5分。起動を待つ間は「角度を計算する準備をしています」と出す）。手の姿勢が出なかった（422）ときは、撮り直してもらう。それでもだめなら採寸を止める。角度がないので採寸は保存されず、ケースは `measuring` のまま。動画は保存しないので、もう一度撮影からやり直す（画面にもそう伝える）。MediaPipeの角度で代わりにはしない | MediaPipeだけの角度では、曲がったまま固まった指の精度が不安なため（チームの判断） |

## 作る順番

1. 11/7の朝に、SAM 3D Bodyの重みの利用申請を出す（承認制。**承認が遅れると採寸が完成しない**ので最優先）
2. 開発の途中は、MediaPipeの角度（方法A・B）で仮に通してよい。ただし、デプロイ版では使わない
3. 11/8 20:00の通しのテストまでに、`hand-mesh` を組み込む
4. 11/9の検証で、メッシュ復元とMediaPipeの角度を、分度器で測った値と比べる。結果はOT画面の比較の表示と、ピッチで使う

## 引き受けること

| 危険 | 対策 |
|---|---|
| GPUのサービスが止まると、採寸の流れ全体が止まる | 自動の再試行。デモと審査の時間帯だけ、最小台数を1にして温めておく（[ADR-0009](0009-gpu-placement.md)） |
| 重みの承認が間に合わない | 11/7の朝に申請する。11/8 12:00になっても承認されなければ、21:00の打ち合わせを待たずに全員で集まり、MediaPipeの角度で代わりにすることを含めて決め直す |
| 曲がったまま固まった指で、メッシュ復元の角度がずれる（学習データの分布の外） | MediaPipeの角度を並べてOT画面に出し、差が15度を超える関節は目立たせる。OTは差し戻しのコメントで直す点を伝え、持ち主（家族）が「詳しく見る」で値を直す（MVPではOT画面から直接は直さない） |
| 同意しない人は使えない | 同意の画面で、送る理由・送る量・保存しないことを分かりやすく書く |
