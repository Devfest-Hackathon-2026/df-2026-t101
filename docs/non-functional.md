# 非機能要件

> **このドキュメントで決めたこと**
> 1. 財源は2つ（ハッカソンの20ドル、個人のクレジット約50,600円）。まずハッカソンの20ドルに収まるよう、開発中はモックと安いモデルを使い、Gemini 4 Argonは調整とデモに絞る。足りない分は個人のクレジットで払う。見積もりは定価で行い、予算アラートに加えて、アプリ側でも1日の概算コストで生成を止める。
> 2. 形の生成の目標は、最初のプレビューまで75秒（中央値。手の3Dメッシュからカバーの殻を作る計算 10〜20秒を含む）、最大170秒。初回の手のモデルの読み込みは、Wi-Fiで10秒以内。安全の決まり（手のひら側を開ける・手首を覆わない・装具にしない）は、描いたあとの自動の検査とOTの確認の二重で守る（§8）。
> 3. 手の映像は、生成APIにもGeminiにも渡さない。端末の外に出るのは、手を切り抜いたフレーム（最大8枚）だけで、全員から同意を得て、手の3Dメッシュを作る（`hand-mesh`）ためだけに使い、保存しない。作った手の3Dメッシュ（写真ではない）は、同意を得て保存し、持ち主と担当のOTだけが読める。

関連：[architecture.md](architecture.md)、[generation-pipeline.md](generation-pipeline.md)、[data-model.md](data-model.md)

### 2.4 予算を超えないための仕組み

| 仕組み | 設定 | 補足 |
|---|---|---|
| 予算アラート | 個人の請求先アカウント（円建て）に、3,000円（≒ハッカソンの20ドルを使い切った目安）・5,000円・10,000円・30,000円の予算。通知先は4人全員 | 予算は支出に上限をかけない（通知するだけ）。最初の通知まで数時間かかることがある。既定ではクレジットを差し引いた額で判定するので、**クレジットを含めない（差し引かない）設定にして、総額で判定する**。クレジットの消費額そのものでアラートを出す機能は、確かめられなかった |
| 毎日の確認 | 毎日21:00の打ち合わせで、Cloud Consoleの請求の画面と、Cloud Runの最小台数を確かめる | 請求データの遅れと、GPUの最小台数の放置に備える |
| アプリの1日の上限 | GeminiとGPU推論の概算費用を合算した `estimated_cost_usd` が `DAILY_COST_LIMIT_USD`（既定$15）に達したら、新しい処理を始めない。GPUは1回あたり固定の見積もり額（$0.40。まばらに呼んだときの、起動と待機を含む値）を、始めるときに足す。Geminiは呼び終えたあとでトークン数から足す | 両サービスが共通のFirestoreで、確認と加算を1つのトランザクションで行う。精算はしない（見積もりは多めに取っている） |
| 回数の上限 | 1人1日あたり生成10回・微調整30回・聞き取り60回・GPU推論20回。全体で1日あたり生成100回・GPU推論100回 | GPUは失敗と自動再試行も数える。直接APIを呼んだ場合も制限する |
| GPU推論の時間上限 | 1回60秒で中断する | HTTP接続の切断だけに任せない。ただし、費用の大半は推論そのものではなく、起動と止まるまでの待機（インスタンスが動いている時間）にかかる |
| 停止スイッチ | 共通の `settings/runtime.generation_enabled=false` でGeminiと `hand-mesh` の新規処理を止める。未設定・読み取り失敗でも開始しない | 各サービスの `GENERATION_ENABLED=false` でもそのサービスを止められる。全体停止には共通設定を使う |
| 課金の自動停止 | 使わない | 予算を超えたら課金アカウントを外す公式の方法（Pub/Sub＋関数）はあるが、全サービスが止まり、リソースが消えるおそれがあるため。デモの直前に止まる危険の方が大きい |
| インスタンスの上限 | 最大3 | 想定外のアクセスで増えすぎないように |

このアプリ内の費用上限は、GeminiとGPU推論の回数から見積もった概算のもの（GPUの$0.40は「まばらに呼んだ場合」の見積もりで、続けて呼ぶと実際より多めになり、デモの時間帯の最小台数1の費用は入らない）。GPUのコールドスタート・待機中、Build・Storageなどの費用まで含む請求の上限ではない。GPUの最小台数の管理と予算アラート（§2.6、ADR-0009）も併用する。GPU推論の単価・開始回数・実行秒数は別々に記録し、請求額との差を確認する。


### 2.5 どのクレジットで何を動かすか

| 財源 | 金額 | 使い道 |
|---|---|---|
| ハッカソンの配布クレジット（クーポンコード） | 20ドル | 個人の請求先アカウントで引き換える |
| 個人のGoogle Cloudクレジット | 約50,600円（¥47,462＋¥3,165）。使い切ると登録したカードに請求される | 同じ請求先アカウントに入っている |

- 決めたこと：クーポンを個人の請求先アカウントで引き換え、2つのクレジットを1つの請求先にまとめる。アプリと `hand-mesh` は同じ1つのプロジェクトに置き、その請求先につなぐ（[ADR-0009](adr/0009-gpu-placement.md)）
- 理由：請求先を付け替える手間と、プロジェクトをまたいだ呼び出しの不確かさがなくなる
- 引き受けること：どちらのクレジットから先に減るかを、分けて見られない。費用は総額で見張る
- 要確認：クーポンの規約で、使えるサービス（AI Studioには使えないとされている）や、引き換える請求先アカウントに制限がないか。引き換える前に読む
- 円とドルの換算は、1ドル＝150円の仮定（実際のレートで要確認）

## 3. セキュリティ

| 項目 | 決めたこと |
|---|---|
| 秘密情報 | Geminiはサービスアカウントで呼ぶので、APIキーを使わない。秘密の値は、`hand-mesh` の結果トークンの署名の鍵（`MESH_RESULT_HMAC_KEY`）だけで、Secret Managerに置き、リポジトリには入れない。サービスアカウントの鍵ファイルは作らない（手元では `gcloud auth application-default login` を使う）。Firebaseのウェブ用の設定値は秘密ではないが、チームの決まりに合わせてリポジトリには入れず、`--dart-define-from-file`（`env/*.json`、`.gitignore` に入れる）で渡す。見本として `env/example.json` だけを入れる。APIキーには、HTTPリファラーと使えるAPIの制限をかける |
| 認証 | Googleログインだけを使う（匿名ログインは、スマホとPCで引き継げないため使わない）。生成APIは、すべてのリクエストでIDトークンを検証する |
| 権限 | ケースは持ち主と、依頼されたOTだけが読める。OTかどうかは `therapists` の許可リストで決める。ブラウザからFirestore・Storageには書き込めない（[data-model.md §4](data-model.md#4-セキュリティルールの方針)） |
| 入力の検証 | すべての入力をPydanticで型と範囲を確かめる。チャットの文は1回500文字まで |
| AIの出力 | Geminiの出力は、スキーマと範囲チェックを通るまで使わない。OpenSCADに渡すのは、サーバーが型付きの値から作った `-D` の引数だけで、AIの文字列をコードやコマンドに混ぜない。プロンプトインジェクション（チャットで「範囲を無視して」などと書く）があっても、範囲チェックで止まる |
| OpenSCAD | ユーザーやAIが書いたコードは実行しない。ジョブごとに作業フォルダを分け、60秒で打ち切る。コンテナは非rootユーザーで動かす |
| 通信 | HTTPSのみ。CORSは自分たちのHostingのURL（プレビューチャンネルを含む）だけを許す |
| 乱用対策 | 生成APIと `hand-mesh` の双方で、回数の上限、1日のコストの上限、共通の停止スイッチ。App Check（reCAPTCHA Enterprise。月1万回まで無料）は拡張機能 |
| ログ | ログに残すのは、ID、処理時間、トークン数、エラーコードだけ。チャットの文と採寸の数値はログに出さない |
| 依存関係 | Python・Dart・TypeScript／JavaScriptのライブラリは、バージョンを固定する |
| 提出前 | 提出用のリポジトリにpushする前に、手元で秘密情報の検査を行う |

## 4. プライバシー

| 項目 | 決めたこと | 理由 |
|---|---|---|
| 手の動画・写真 | ブラウザのメモリの中だけで扱い、保存しない。生成APIとGeminiには送らない（受け取る口がない）。手の検出（MediaPipe）と1円玉の検出（OpenCV.js）は、端末の中で行う。MediaPipe・OpenCV.jsの本体とモデルは自分たちのHostingから配る。端末の外に出るのは、次の行の切り抜いたフレームだけ | 手の映像は体の情報で、他人に見られたくない人がいる |
| 手のメッシュ復元 | 撮影の前に全員から同意を得て（同意しないと採寸に進めない）、手を切り抜いたフレーム（最大8枚、長い辺512px）を、ブラウザから `hand-mesh` に直接送る。フレームはメモリの中だけで処理し、保存しない・ログに残さない。処理はシンガポールで行う（[ADR-0008](adr/0008-hand-model-capsules.md)・[ADR-0010](adr/0010-hand-mesh-fusion.md)） | 手の3Dメッシュを作るため。手の映像は、病気や障害が分かる情報になりうるので、送る内容をはっきり示して同意を得る（要配慮個人情報に当たるかは要確認） |
| 手の3Dメッシュ | フレームから作った手の3Dメッシュ（頂点と三角形だけで、写真や肌の色は入らない）を保存する。大きさを合わせる前の生メッシュは `hand-mesh` が、実寸のメッシュは生成APIが、ケースの下に置く（[data-model.md §3](data-model.md#3-cloud-storageのパス)）。読めるのは持ち主と担当のOTだけ（生メッシュはブラウザから読めない）。ケースを消すと一緒に消える。Geminiには渡さない（Geminiに渡すのは、カバーとクリップの確認用画像に重ねた手の絵だけ） | 作った形が手に合うかを、本人・家族・OTが3Dで確かめるため。微調整のたびに作り直さずに済むため。手の形は体の情報なので、写真ではないこと・何のために保存するか・消し方を同意の画面に書く（同意の文の版 `mesh-consent-2`） |
| サーバーに送るもの | 選択式の質問の答え、チャットの文、採寸の数値（mm・度）、手の3Dメッシュの番号（`mesh_id`。メッシュそのものはブラウザから送らない）、色と模様の選択 | — |
| Geminiに渡すもの | 選択式の質問の答え、チャットの文、採寸の数値、部品の引数、3Dモデルの画像（手にカバーとクリップと道具の棒を重ねたもの）。名前・メールアドレス・写真・手のメッシュのデータは渡さない | 必要なものだけを渡す |
| Geminiの処理場所 | `global` のため、日本の外で処理されることがある | Argonが東京で使えないため。渡すのは上の最小限の情報だけにする。国内での処理が必要になったら、東京で使えるモデル（`gemini-2.5-flash` など）に切り替える |
| AIの学習への利用 | 公式に「事前の許可や指示なしに、顧客のデータをAI・MLモデルの学習や調整に使わない」と書かれている（Agent Platformのデータの扱いのページ、Service Specific Terms 第18条）。ピッチで述べてよい | — |
| Geminiのキャッシュ | 送った内容は、既定で最長24時間メモリにキャッシュされる。プロジェクトの `cacheConfig` を `disableCache: true` にして止める（Cがデプロイのときに設定）。リクエストと応答の記録（request-response logging）は既定で無効のままにする。不正利用の監視のために、怪しいと判定されたプロンプトは最長90日保存されることがある | 健康に関わる会話を、要らないところに残さないため |
| 病名などの情報 | S0とS2に「病名などの詳しい情報は入れなくて大丈夫です」と書く | 要らない健康情報を集めない |
| 同意 | 初めて撮る前に、何を送り何を保存するか（フレームは保存しない、手の3Dメッシュは保存する）を1画面で示し、同意を得る（文の版 `mesh-consent-2`）。同意は生成APIが日時と文の版をケースに記録し（`POST /consent`）、`hand-mesh` と `PUT measurement` がその記録を確かめる（ブラウザの自己申告だけに頼らない）。同意しない場合は採寸に進めない | — |
| 保存期間 | 審査が終わったら（2026年12月まで）、デモのデータ（手の3Dメッシュを含む）を消す | — |

## 5. 対応ブラウザ

| 端末 | ブラウザ | 対応 | 根拠・備考 |
|---|---|---|---|
| iPhone | Safari（iOS 17以上） | 対応 | MediaPipe 1.2.2にはSIMDなしの版が入っていないため、Wasm SIMDが要る（Safari 16.4以上）。WebGL2はSafari 15以上。Flutterは既定でCanvasKitを使う。日本語入力の既知の不具合に注意する（[screens.md S2](screens.md#s2-やりたいこと選択式の質問任意のチャット)） |
| Android | Chrome（最新の2版） | 対応 | — |
| PC | Chrome・Edge（最新） | 対応 | プレビューとOT確認の主な環境 |
| PC | Safari（macOS 最新） | できる範囲で | — |
| すべて | Firefox | できる範囲で | — |

- アプリの中のカメラ（`getUserMedia`）とMediaPipeには、HTTPSが必要（Hostingなら満たす。開発中は `localhost` なら使える。PCのアドレスにスマホから `http://` でつないでもカメラは使えない）
- スマホは背面カメラ、PCはWebカメラを使う。iPhoneのSafariでアプリの中のカメラが使えるか（`playsinline` の扱いを含む）は要確認（11/8に実機で確かめる。だめなら「撮った動画を選ぶ」を主にする）
- OpenCV.js（約11MB、圧縮して約3.5MB）は、Web Workerが使えるブラウザなら動く。読み込みに失敗しても、タップと色で探す方法で1円玉を指定できる
- 11/7中に、iPhoneのSafariとAndroidのChromeの実機で、撮影 → 手の検出 → 3D表示が動くかを確かめる（[tasks.md](tasks.md)）。iOS SafariでMediaPipeのGPU処理が正しく動くかは公式には保証がないので、だめならCPU処理に切り替える

## 6. アクセシビリティ

- 起動時に `SemanticsBinding.instance.ensureSemantics()` を呼び、読み上げ用の情報を有効にする（Flutter Webは既定で無効）
- 押せる範囲は48px以上。ドラッグする点のハンドルは見た目より大きく反応させる
- 文字入力には選択肢を添え、音声入力（OSの機能）を案内する
- 色だけで状態を伝えない
- 片手で操作できるよう、主なボタンは画面の下に置く

## 8. 安全

カバーは「こぶしの外側にかぶせるだけ」の道具で、指や関節を固定・矯正するもの（装具）にはしない（[ADR-0011](adr/0011-dorsal-cover.md)）。次の決まりを、どの段階でも外さない。

| 決まり | どう守るか | 理由 |
|---|---|---|
| 握った指を無理に開かせない | カバーは指の外側にかぶせるだけ。指と手のひらの間に物を差し込まない。撮る形も「いつもの握った形のまま」 | 固まった指を開かせると痛みやけがのもとになる |
| 手のひら側は必ず開けておく | 殻を手のひら側の切る面で切る（[generation-pipeline.md](generation-pipeline.md)）。描いたあとの検査（R6）で、切る面より手のひら側に頂点がないことを確かめる。不合格なら版を出さない。AIや画面の操作でこの検査を外せない | 手のひら側まで覆うと、指を固定する装具になる。着け外しのたびに指を開かせることにもなる |
| 手首を覆わない | 手首側を切る位置を、手首から25mm以上にする（範囲チェック）。描いたあとの検査で、手首から25mm以内に頂点がないことを確かめる | 手首の動きを妨げない。手首を固定すると装具になる |
| 角を丸める | 殻は切る面となめらかにつなぎ、ふちの丸みを1.5mm以上にする（`MIN_EDGE_RADIUS_MM`）。スリット・空気穴のふちも面取りする | 皮膚を傷つけない |
| 手に食い込まない | 内側の面と手の距離が、すき間（`HAND_CLEARANCE_MM`。フェルトの厚みを含む）以上あることを検査する。内側にフェルトかスポンジを貼るよう、ダウンロード画面で案内する | 採寸の誤差を吸収し、圧迫を防ぐ |
| 痛みや赤みが出たら使うのをやめる | プレビュー・ダウンロードの画面と印刷ガイドに必ず書く。最初は短い時間から試すよう書く | 合わない形を使い続けると、皮膚を傷める |
| 使う前にOTが確かめる | 印刷用STLは、OTが「確認済み」にした版だけ渡す（デモのケースを除く）。OTの確認項目に「手のひら側が開いていて、手首を覆っていない」を入れる（[api.md §3.7](api.md#37-post-v1casescase_iddesignsdesign_idapproval)） | 自動の検査とOTの目の二重にする |
| 口に入れる部品は作らない | スプーンのクリップは柄を挟むだけ。食べ物や口に触れる部分は作らない | 食品に触れる材料の安全は保証できない |

## 9. 印刷

| 部品 | 材料 | 刷る向き | 備考 |
|---|---|---|---|
| カバー本体 | PLA | 手のひら側を切った面を下にする | 殻なので、内側（凹んだ面）にはサポートが要る。跡はフェルトで隠れる。外側はサポートなしで刷れる形にする |
| C字クリップ | PETGが望ましい（PLAより粘りがあり割れにくい）。なければPLA | 輪が机と平行になる向き | 縦に刷ると積層の境目から割れやすい。サポートなしで刷れる形にする |
| TPUの筒（任意） | TPU | 筒を立てる | 挟む力をTPUに任せ、PLAのクリップの割れを防ぐ。太さの違う道具には筒だけ刷り直す |

- 大学の3DプリンタでPETG・TPUが使えるかは要確認（11/9の朝に確かめる）。使えなければ、クリップはPLAで刷り、壁の厚さと根元の切り欠きでしなりを作る（[ADR-0012](adr/0012-c-clip-dovetail.md)）
- 刷る設定の目安（層の高さ、壁の数、充填率）は [parts-library.md](parts-library.md) に書く
- ベルト（面ファスナー、幅25mm）とフェルト（厚さ約1mm）は市販のものを使う。用意するものとしてダウンロード画面で案内する
